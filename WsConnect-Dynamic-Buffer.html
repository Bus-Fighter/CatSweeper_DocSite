    Dynamic Buffer Size in WsServer and WsClient

    Overview

    Both WsServer and WsClient now use dynamic buffering to handle WebSocket messages of any size efficiently.

    How It Works

    Previous Implementation (Fixed Buffer)

    // Old approach - limited to bufferSize bytes
var buffer = new byte[bufferSize];
var result = await ws.ReceiveAsync(buffer, token);
// If message > bufferSize, it would be truncated!

    New Implementation (Dynamic Buffer)

    // New approach - handles messages of any size
var chunkBuffer = new byte[bufferSize];  // Fixed chunk size for reading
var messageBuffer = new List<byte>();    // Dynamic accumulator

do {
    result = await ws.ReceiveAsync(new ArraySegment<byte>(chunkBuffer), token);
    
    // Append chunk to message buffer
    for (int i = 0; i < result.Count; i++) {
        messageBuffer.Add(chunkBuffer[i]);
    }
} while (!result.EndOfMessage);  // Keep reading until complete message

var completeMessage = messageBuffer.ToArray();

    Key Improvements

    1. Handles Large Messages

    • Messages larger than the initial bufferSize are now fully received
    • No data loss or truncation
    • Memory grows dynamically as needed

    2. Efficient for Small Messages

    • Small messages don't waste memory
    • Only allocates what's needed for the actual message size

    3. Chunk-Based Reading

    • Reads data in fixed-size chunks (configurable via constructor)
    • Default chunk size: 1024 bytes
    • Can be adjusted based on your typical message size

    4. EndOfMessage Detection

    • Uses WebSocket's built-in EndOfMessage flag
    • Ensures complete messages are received before processing
    • Prevents partial message handling

    Configuration

    The bufferSize parameter now represents the chunk size for reading:

    // Small messages (e.g., JSON commands)
var server = new WsServer("http://localhost:8080/", bufferSize: 1024);

// Large messages (e.g., file transfers)
var server = new WsServer("http://localhost:8080/", bufferSize: 8192);

// Custom chunk size
var server = new WsServer("http://localhost:8080/", bufferSize: 4096);

    Choosing the Right Chunk Size

    Use Case Recommended Chunk Size Reason
    JSON messages (< 10KB) 1024 - 2048 bytes Minimizes memory overhead
    Binary data (10KB - 100KB) 4096 - 8192 bytes Balances throughput and memory
    File transfers (> 100KB) 8192 - 16384 bytes Maximizes throughput

    Memory Characteristics

    Memory Usage Pattern

    Message Size: 5KB, Chunk Size: 1024 bytes

Iteration 1: chunkBuffer[1024] + messageBuffer[1024]     = ~2KB
Iteration 2: chunkBuffer[1024] + messageBuffer[2048]     = ~3KB
Iteration 3: chunkBuffer[1024] + messageBuffer[3072]     = ~4KB
Iteration 4: chunkBuffer[1024] + messageBuffer[4096]     = ~5KB
Iteration 5: chunkBuffer[1024] + messageBuffer[5120]     = ~6KB (final)

Peak Memory: ~6KB (vs fixed 5KB for exact-size buffer)

    Memory Trade-offs

    Advantages:

    • ✅ No message size limits
    • ✅ Adapts to actual message sizes
    • ✅ Small overhead per message

    Disadvantages:

    • ⚠️ Slight memory overhead from List<byte> growth
    • ⚠️ Some GC pressure from intermediate allocations

    Performance Optimization Tips

    1. Reuse Message Buffer (Advanced)

    If you're processing many messages, consider using ArrayPool:

    private async Task ReceiveMessagesAsync(WebSocket ws, CancellationToken token)
{
    var chunkBuffer = ArrayPool<byte>.Shared.Rent(bufferSize);
    var messageBuffer = new List<byte>(bufferSize);

    try {
        while (ws.State == WebSocketState.Open) {
            messageBuffer.Clear();
            WebSocketReceiveResult result;
            
            do {
                result = await ws.ReceiveAsync(
                    new ArraySegment<byte>(chunkBuffer, 0, bufferSize), token);
                messageBuffer.AddRange(
                    new ArraySegment<byte>(chunkBuffer, 0, result.Count));
            } while (!result.EndOfMessage);
            
            // Process messageBuffer...
        }
    } finally {
        ArrayPool<byte>.Shared.Return(chunkBuffer);
    }
}

    2. Pre-allocate Message Buffer

    If you know the typical message size:

    var messageBuffer = new List<byte>(expectedMessageSize);

    3. Adjust Chunk Size Based on Network

    • Local network (low latency): Smaller chunks (1-2KB)
    • Internet (higher latency): Larger chunks (4-8KB)

    Example Usage

    Sending Large Messages

    // Server can now receive messages of any size
var largeData = new byte[1024 * 1024]; // 1MB
await client.SendAsync(largeData, SocketMessage.Type.Binary);
// Server will receive it in chunks and reassemble

    Receiving Messages

    // Client receives complete message regardless of size
var message = await client.Receive();
Console.WriteLine($"Received {message.data.Length} bytes");

    Testing

    Test Case: Large Message

    [Test]
public async Task TestLargeMessage()
{
    var server = new WsServer("http://localhost:8080/", bufferSize: 1024);
    server.Start();
    
    var client = new WsClient("ws://localhost:8080", bufferSize: 1024);
    await client.Connect();
    
    // Send 100KB message with 1KB chunks
    var largeMessage = new byte[100 * 1024];
    new Random().NextBytes(largeMessage);
    
    await client.Send(largeMessage);
    
    // Should receive complete message
    var received = await server.Receive();
    Assert.Equal(100 * 1024, received.data.Length);
}

    Migration Guide

    No code changes required! The API remains the same:

    // Old code still works
var server = new WsServer("http://localhost:8080/");
server.OnMessageReceived += (client, msg) => {
    Console.WriteLine($"Received: {msg.data.Length} bytes");
};

// Messages of any size are now handled automatically

    • ✅ Backward compatible with existing code
    • ✅ Works with all WebSocket message types (Text, Binary)
    • ✅ Handles fragmented messages transparently
    • ✅ No breaking changes to public API

    1. Unlimited message size support

    4. Zero breaking changes to existing code
